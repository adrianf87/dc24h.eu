# CI Debiana 13 na własnym runnerze

`.github/workflows/proxmox-debian13.yml` uruchamia się automatycznie po push do `main` i gałęzi `alpha-*`, a także przez `workflow_dispatch`. Nie wykonuje kodu pull requestów z forków na własnym runnerze. Istniejąca grupa `proxmox-vm100` przydziela VM kolejno, bez anulowania aktywnego przebiegu.

Dotychczasowe zadanie startu wymaga wyłączonej VM 100, włącza ją ograniczoną komendą SSH i czeka na stan running. Testy używają istniejących etykiet `[self-hosted, Linux, X64, ci-controller]`. Zadanie sprawdza Debian 13 w `/etc/os-release` i wyświetla wersje CMake, C++ oraz ncdc. Macierz wykonuje **Debug i Release kolejno** (`max-parallel: 1`, `fail-fast: false`) w osobnych katalogach `build-debian13-Debug` / `build-debian13-Release`. Każdy przebieg ustawia `DC24H_REQUIRE_INTEGRATION_TESTS=ON`, kompiluje C++20 dwoma procesami i wykonuje wszystkie zarejestrowane testy CTest, w tym prawdziwe ncdc, MariaDB i Apache HTTPS. Nie ma progu opartego na historycznej liczbie testów.

Istniejące zadanie wyłączenia działa po całej macierzy, także po błędzie testów, jeżeli start VM powiódł się. Zachowano ścisłe sprawdzanie klucza hosta SSH, nazwy sekretów, wymóg własności VM, timeouty i komendy zasilania. Jeżeli VM już działa, start kończy się błędem, bez przejmowania jej i późniejszego wyłączenia. Administrator repozytorium przygotowuje runner i istniejące sekrety `PVE_VM100_SSH_KEY` / `PVE_VM100_KNOWN_HOSTS`; wartości sekretów nie trafiają do repozytorium.

Przed uruchomieniem przygotuj CMake >=3.22, kompilator C++20, Python >=3.8, biblioteki deweloperskie utf8proc/OpenSSL/libgcrypt/MariaDB, OpenSSL CLI, ncdc, narzędzia instalacyjne i serwer/klienta MariaDB oraz Apache2. Brak wymaganych narzędzi integracyjnych zatrzymuje konfigurację CMake. Zadanie testów C++ nie instaluje ani nie wymaga systemowego pakietu Node/npm. Zadanie WebAdmin na Ubuntu nadal używa **Node 22** przez `actions/setup-node@v5`.

Wszystkie trzy kroki checkout używają teraz `actions/checkout@v6`; zachowano `persist-credentials: false` własnego runnera. [Checkout v6](https://github.com/actions/checkout/blob/v6/action.yml) i [setup-node v5](https://github.com/actions/setup-node/blob/v5/action.yml) deklarują środowisko akcji Node 24, dostarczane przez zgodny Actions Runner. Jest ono niezależne od `node-version: 22` budującego WebAdmin. Nie jest potrzebna instalacja Node 24 przez apt ani zmienna ukrywająca ostrzeżenie. Runner musi obsługiwać akcje Node 24; utrzymuj jego aktualną wersję.

Lokalnie sprawdzaj workflow przez `actionlint`; `.github/actionlint.yaml` deklaruje własną etykietę `ci-controller`. Publikacja workflow automatycznie uruchamia zadania push. Można podać od razu ich adres/status, bez oczekiwania na koniec i bez deklarowania zdalnego sukcesu. Wyniki lokalnej regresji i zdalnego runnera są odrębne.
