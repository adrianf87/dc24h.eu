## Selection contract

`search/features.hpp` defines `Selection`, `FeatureCode`, `FeatureError` and `FeatureFilter`. Feature identifiers contain three uppercase ASCII letters followed by an uppercase letter or digit. Matching is exact, case-sensitive and revision-sensitive: `ADC0` and `ADC1` differ. Unknown valid identifiers are accepted without an extension whitelist. Encoding the four bytes into a 32-bit value is injective and uses no hashing, locale or Unicode normalization.

A Selection contains required and excluded names. All required features must occur in the recipient's public `INF SU`; no excluded feature may occur. Required-only, excluded-only and mixed selectors are supported. Empty Selection matches all ready users for ordinary B/D/E routing. FSCH itself still requires a nonempty selector header. The combined application limit is 32; duplicates, overlapping required/excluded names and malformed names are refused before copying strings. Invalid local objects and oversized strings cannot trigger partial compilation or token registration. The original checked order and spellings remain owned by the plan.

The filter compiles selectors once, keeps a bounded array of exact codes, and matches an advertised set with a 64-bit required-feature mask. Matching performs no allocations. Duplicate advertised labels have set semantics; unrelated malformed labels cannot satisfy a selector. Public profiles retain their existing validation and 128-feature ceiling; this module does not relax it or reinterpret profile text.

## Session and wire integration

Core preparation and both stateless and active-token dispatch use the same immutable compiled FeatureFilter. Selection comes from FSCH; advertised capabilities come only from the current SessionManager User/profile derived from validated public INF. `HSUP AD...` / `RM...` negotiates capabilities with the hub and does not populate or remove public `SU`. A client may announce different features through these two mechanisms, as specified by the [ADC protocol](https://adc.sourceforge.io/ADC.html).

Ready snapshot lifetimes still govern delivery. The source receives its own F request only when it matches. Empty/canceled SU satisfies negative-only selectors and no positive selector. A later valid `BINF ... SU...` affects the next query immediately; dispatch also rechecks every planned recipient so a lost required feature or a newly excluded feature suppresses delivery. Capability gains and new logins do not expand an already prepared snapshot. Negotiating users are excluded; source spoofing, readiness, disconnect/SID reuse and cancellation protections remain unchanged.

SCH semantic validation uses the shared FeatureCode parser. One immutable shared SearchFrame retains the original F header, selector order, criteria, TO/TR, unknown fields and numeric spelling. No rewriting to B, widening to all users or fallback occurs when no user matches. Empty fanout releases its TO immediately. Invalid selectors do not reserve a TO or queue any request; fixed recoverable search errors contain no query data. Existing per-peer queue/transport failure isolation and token caps apply. See [Search Routing](SEARCH_ROUTING.md), [Search Core](SEARCH_CORE.md), [ADC SCH](ADC_SCH.md) and [INF Updates](INF_UPDATES.md).

## Verification and scope

The `search.features` unit suite checks validation/ownership/allocation failure, all required/excluded combinations over representative feature sets, every advertised subset, the 32-bit boundary, exact unknown revisions and allocation-free matching. Its 270-user FSCH fanout verifies multipage snapshots, current positive/negative rechecks, late capability gains, late joins, shared frames and token cleanup. `search.features.process` tests fragmented mixed ADC/ADCS fanout, live SU updates/cancellation, SUP independence, issuer membership, all 32 selectors, invalid/overlapping selectors, reusable empty-query tokens, source/state failures and log/API/chat privacy.

`adc.feature.ncdc` and `adcs.feature.ncdc` use a tiny actual ncdc share, wait for indexing, and submit `FSCH ... -TCP4 ...` from a nonmatching peer. Plain ADC verifies the FSCH frame and the DRES produced by ncdc with its file path and opaque token. ADCS verifies the response through ncdc's hub window while packet captures remain encrypted. The nonmatching issuer receives no echo. Existing name/filter/TTH, login/chat/reconnect tests remain enabled.

Only request feature routing is delivered. RES remains explicitly unsupported (125); ncdc producing a DRES is an interoperability assertion, not a claim that result forwarding works. No file index in the hub, client transfer, UDP result service, search-specific flood policy/history, SQL migration, endpoint, setting or WebAdmin search page is added. Code/wire diagnostics remain EN/US UTF-8; documentation is mirrored in US/PL. The branch preserves history and is published separately from main.

The installed [ncdc 1.23.1 source](https://dev.yorhel.nl/download/ncdc-1.23.1.tar.gz), `src/hub.c` adc_handle prefilter, advertises ADC0 publicly but its own incoming F-header prefilter recognizes only TCP4. Its interoperability test therefore uses negative-only `-TCP4`; positive/mixed/unknown selectors are verified by raw protocol peers and the C++ suites. This client limitation does not change server SU matching.
