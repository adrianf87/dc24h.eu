# Beta-0.9.5–0.9.8 — Stage II: cold-start authenticity and account/device safety

Scope: work unit **2/10**, [Issue #242](https://github.com/adrianf87/dc24h.eu-high-starter/issues/242), shared `beta-0.9.x-stage-full` and draft [PR #243](https://github.com/adrianf87/dc24h.eu-high-starter/pull/243). Source and tests are development-only. **No private-state v2 schema/key migration or live authentication preflight is authorized.** A separately documented Owner architecture/migration/rollback decision is required before 0.9.6 can be activated.

## 0.9.5 — Owner-keyed five-store authenticity proposal, not deployment

The in-memory-only `scripts/beta09_stage2_auth_proposal.py` gives the Owner a reviewable *candidate* contract. It cannot open/write private files, store a key, sign an installed gateway, rotate a real key or approve a backup. Synthetic tests prove only the proposed arithmetic and refusal predicates.

- Bind exactly five stores (`audit.jsonl`, `mfa.json`, `passkeys.json`, `rate-limits.json`, `replay.jsonl`) with their exact byte counts and SHA-256 digests; bind the separate matched MariaDB-v11/private recovery pair digest as an additional authenticated field. No file mtime, inode or process memory hash substitutes for a stable trusted root.
- Proposed canonical domain-separated HMAC-SHA256 metadata includes schema `2`, bounded monotonic `generation`, detached `key_id`, `previous_mac`, pair digest, five per-file digests and `mac`. A **separately retained Owner-controlled checkpoint** pins `(generation, mac)`; all five bytes must match the pin on a cold process. A subsequent candidate needs exactly `generation + 1` and the pinned predecessor MAC. A replayed valid old manifest fails against a newer checkpoint.
- The key (256 random bits) and checkpoint must live outside both SQL and the five state files, with independent owner-only custody, encryption-at-rest/backup policy and verified off-host disaster-recovery copy. A file MAC without the independently protected checkpoint would *not* stop offline rollback. An HMAC does **not** establish nonrepudiation or independent human approval.
- **Rotation design:** Owner-approved two-key transition must bind the old authenticated generation, new key identifier and a new generation under a separately verified new checkpoint. No silent rotation, trust-on-first-use, fallback to a missing key or reset to generation 1. Lost key/checkpoint is **NO-GO** until independently verified key/checkpoint recovery, not an opportunity to generate a replacement.
- **Migration design, awaiting approval:** Stop every gateway writer, produce a matched six-component backup, pin a verified pre-migration trust root, dry-run a shadow authenticated generation on a fresh destination, test failed fsync/partial capture/rollback, then independently authorize a controlled cutover. All five stores and the out-of-band checkpoint need crash-consistent commit/recovery rules. Since live TOTP, limiter and passkey writes are separate fsync/rename operations, simply adding a detached manifest *after* writes cannot prove atomic online consistency. Do not enable runtime authentication until a specific journal/commit protocol and v1 fallback/rollback sequence are reviewed, implemented and tested.

## 0.9.6 — Existing MFA/replay and limiter cold-start boundaries

The standalone `tests/beta09_stage2_cold_start_tests.py` exercises the **existing** optional stopped-writer `beta08_recovery_auth.py` flow with a separate disposable HMAC key/checkpoint. It rewrites each of the five synthetic snapshot files to another same-size value and restores mtime; every changed source fails the matched snapshot authentication on a fresh verify. The test does not claim runtime startup enforces this offline recovery MAC. Existing Node tests still enforce one-use TOTP across normal restarts, missing replay-ledger refusal, no quota reset on a clean limiter restart, clock rollback refusal and in-process catalog-fingerprint invalidation.

**Implementation blocked pending Owner approval:** The active schema-1 `mfa.json`, `replay.jsonl`, `rate-limits.json` and passkey catalog have no durable independent runtime authenticity checkpoint. A wholly offline valid-shaped rewrite *followed by a cold restart* cannot currently be distinguished from authorized state by the production gateway. Therefore no unconditional cold-start-tamper, anti-rollback, hardware passkey or 429-after-hostile-rewrite claim is made. The synthetic design-model result explicitly emits `runtime_authenticity_activated: false`.

## 0.9.7 — WebAuthn, two sessions, revocation and post-write exception

`remote-gateway.ts` now records the actor's credential IDs before enrollment verification. If a ceremony writes a new credential and then throws **before returning success**, the catch path rereads the catalog and revokes *all* earlier sessions of that actor; on catalog read failure it clears all sessions. Previously only an explicit `true` result proved persistence, leaving stale siblings alive on this path. The existing failed-completion-audit case remains guarded, while a rejected duplicate finish with no valid pending challenge does **not** revoke an unrelated healthy session.

Node regressions inject durable-write-then-throw and strict completion-audit loss with two independent actor sessions. A genuine ES256 regression runs two overlapping verifications against one signed assertion and asserts exactly one can advance the durable counter. Existing HTTPS Chromium virtual-authenticator coverage signs on two separate devices across a matched five-store restore and refuses a revoked device and stale assertion. This is virtual/software evidence, not physical hardware, synced-passkey security or full C++ authorization certification.

## 0.9.8 — Lost-factor recovery, fallback and EN/PL usability

An offline two-operator-request fixture revokes one actor's lost device, preserves a foreign actor's credential, persists the actor epoch across reopening, and proves the independent TOTP replay ledger does **not** reset. The next unused TOTP step remains usable for a **new** password-authorized gateway login; the fixture itself does not mint a C++ grant. A Playwright EN/PL keyboard test refuses passkey login, clears the entered password, focuses the account field, and permits the existing password+TOTP form without exposing test secrets in rendered text. Recovery requires separately verified identity and explicit stopped-gateway authority; acknowledgments are not cryptographic multi-person approval.
